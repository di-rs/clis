# CLI Playground PostgreSQL Implementation Plan

> **For agentic workers:** Use `executing-plans` to implement this plan task by task, or `subagent-driven-development` if the user chooses delegation. The checklist below records the original plan; see the execution record for the delivered result.

**Goal:** Replace custom metadata file persistence with readable SQLModel queries and PostgreSQL transactions while preserving Playground behavior.

**Architecture:** Keep synchronous domain decisions independent of I/O. The async application uses persistence ports implemented by PostgreSQL adapters with SQLModel sessions and SQLAlchemy transactions. PostgreSQL owns structured state; a small upload-staging module owns durable ZIP files. Boxie remains an HTTP/WebSocket dependency with its own database ownership.

**Tech stack:** Existing Python/FastAPI/Pydantic stack plus SQLModel, SQLAlchemy, psycopg and Alembic, pinned through the root uv workspace.

**Execution correction:** The user requires ports/adapters with synchronous domain logic and asynchronous database operations. Domain values and rules live in `domain.py`; `ports.py` defines the async I/O contracts. The stores are PostgreSQL adapters, not domain objects. Alembic assets live inside the import package so the existing build backend includes them in wheels.

**Spec:** The design below incorporates [issue #71](https://github.com/di-rs/sanctuary/issues/71) with the user's changes: prioritize readability and maintainability, and omit legacy-state import. The original plan is retained below. Current architecture and operation are documented in [Persistence](../persistence.md).

## Execution record

Implemented on `feat/playground-postgres`. The domain contains synchronous Pydantic values and decisions; application services await persistence ports, and PostgreSQL adapters own short transactions. Alembic scripts are packaged inside the Python module, preserving the existing build backend. ZIP validation and durable staging run off the event loop and wait for their workers before cancellation releases source files.

The application, terminal paths, recovery, test fixtures, browser server, native harness, Compose configuration, installer, release script and CI now use PostgreSQL. Provisioning handles an already-initialized database cluster. Documentation covers dedicated credentials, explicit schema upgrades, fresh-state cutover and coordinated backup/rollback. No legacy importer was added.

The coupled application and adapter conversion is delivered as one change rather than the intermediate commits proposed below. Review found and corrected a recovery race against a newer terminal claim and blocking ZIP staging, with regression coverage. Verification includes real PostgreSQL lifecycle tests, browser E2Es, installed-wheel/Compose checks, default tests, Ruff and strict mypy. The native Linux/gVisor tier remains unverified locally; production deployment has not been performed.

## Design and constraints

Use a separate `cli_playground` database and non-superuser login on the existing PostgreSQL service. Own the schema and Alembic history inside this package. Follow [Boxie's database session pattern](../../../../packages/boxie/src/boxie/persistence/database.py), but do not import Boxie's persistence implementation or access its tables. No generic repository framework, backend selector, dual writes, or JSON-file fallback.

Keep public request/response models in `models.py`; SQLModel table classes describe persistence. Reuse field definitions where this reduces duplication without coupling API serialization to the database. Retain Pydantic validation at API and Boxie response boundaries. SQLModel table construction alone is not a substitute for that validation.

Use these tables:

| Table | Purpose and constraints |
| --- | --- |
| `preview` | PR primary key, closure flag, expiry, nullable build identity/status, nullable current revision. Keep the row after expiry/removal so closure survives. Public IDs remain derived from the PR number. |
| `artifact_revision` | Immutable metadata; unique `(pr, revision)` and unique Boxie artifact UUID. Store digest, SHA, CLI list and expiry. Reference the owning PR. |
| `session_binding` | UUID primary key, PR/revision reference, credential hash, sandbox snapshot, pending-stop and attachment fields. Index pending stops and preview references. |
| `create_intent` | UUID primary key matching the Boxie idempotency key; PR/revision, credential hash, request snapshot, claim deadline and abandoned flag. |
| `upload_intent` | Boxie artifact UUID primary key, PR/revision and candidate artifact metadata, build identity, previous revision and irreversible cancellation flag. Candidate metadata exists before publication, independently of `artifact_revision`. |
| `artifact_retirement` | Boxie artifact UUID primary key and completion flag. Keep completed rows to prevent repeat retirement work. |

Use typed columns for identifiers, ordering, lifecycle flags, deadlines and relationships. JSONB is appropriate for the CLI list and validated Boxie request/response snapshots. Do not store whole preview or binding models as opaque JSON documents. Keep nullable build fields consistent with database checks. Enforce that a preview's current revision belongs to that PR with a composite foreign key; create the cyclic preview/revision foreign key after both tables exist.

Use short database transactions. For PR mutations, insert the PR row with conflict handling, then lock that row before checking closure, build order or revision identity. Any operation touching both PR and operation rows locks the PR first. Never hold a transaction or database lock across a Boxie network call or ZIP validation. After each network await, re-read authoritative state before committing its result. Awaiting SQL introduces scheduling points: replace existing assumptions about synchronous reads/writes with explicit transactions and conditional updates.

Keep one Uvicorn worker, the upload semaphore and process-local admission tracking. Transactional storage does not establish replica support. Keep stable URLs, revision identity, credential hashing, build ordering and external API behavior.

There is no legacy-data importer. The first deployment uses an empty database and fresh staging directory. Drain old sessions and pending work before switching; existing previews must be republished. Do not erase old state automatically or silently start the old file-backed application against the new deployment.

## Review focus

Each condition below has a corresponding test in the tasks:

- A PR closes and reopens during upload: that upload remains cancelled.
- Boxie succeeds but the local commit acknowledgement is lost: retry preserves the original UUID and cannot undo a newer result.
- An older attachment completes after its successor: it cannot overwrite or stop the successor.
- A crash occurs between ZIP durability, intent commit and ZIP deletion: recovery can finish or safely discard the work.
- PostgreSQL is unavailable: requests fail explicitly and recovery preserves pending work without interpreting failure as an empty database.

## Completion criteria

PostgreSQL is the sole source of structured Playground state. Alembic owns its schema; ordinary code uses SQLModel sessions. The remaining filesystem code handles staged binary uploads only. Existing lifecycle behavior has real PostgreSQL and API/E2E coverage, with production deployment and backup instructions that reflect the fresh-state cutover.
