# CLI benchmark experiments and confirmation

Accepted by the maintainer on 2026-10-06. This extends the
[harness design](2026-10-06-cli-bench-design.md) with optional experiment metadata,
cooperating process coordination and confirmation cases. It does not change the
Task 1 suite schema.

## 1. Optional experiment metadata

Add three long-only run/check flags: `--experiment ID`, `--hypothesis TEXT`, and
`--change-summary TEXT`. The latter two require an experiment ID. Every tagged
attempt requires both descriptions and a previous-revision build (`-b`), so its
starting SHA is known and verified, not attributed to an unknown supplied binary.
Untagged reference and prebuilt comparisons remain fully supported.

On first use, persist the resolved previous SHA and measurement contract under
`.cli-bench/experiments/ID/`. Later attempts with that ID must use the same
starting SHA and contract. Keep a record for every tagged invocation, including
preparation/correctness/execution failures and no-improvement results. A failed
attempt before full resolution records the requested bindings and error with
unresolved identity explicitly absent; it cannot establish a verified contract.
Export/history include the experiment metadata and attempt references.

The contract fixes the complete suite (including all declared cases and recipe
profiles), harness/generator/engine identities, validator/analysis versions,
resolved build policy, compiler and measurement profile. Paths and candidate
revision are run bindings, not contract identity. Each run also retains actual
input hashes and selected case IDs. Selecting another already-declared case does
not modify the suite; changing a recipe/check/work declaration requires a new
experiment ID. Reports identify the case selection, never make a ratio between
different selections, and retain per-case verified input identities.

Confirmation uses the same declared suite and fixed previous revision, with the
confirmation cases explicitly selected. The record tracks runs submitted to the
harness; it cannot detect experiments performed outside it or prove nobody tuned
against public confirmation cases.

## 2. Cooperating process lock

Use one OS-backed lock per user account on the physical host, independent of
repository and data-directory paths, in an owner-only directory under `/tmp`.
Reject symlinks/wrong ownership. Acquire it before preparation/build/generation and
retain it through warmups, timing, RSS and final validation, so one harness cannot
build while another measures. Resource-consuming `build` and `check` commands
cooperate too; offline report/history/export do not need the lock.

If busy, report that the process is waiting and wait until the lock becomes
available or the caller cancels. Keep cancellation responsive while waiting;
never silently proceed without exclusion. Lock waiting is outside sample/build
deadlines and is recorded separately from benchmark time. OS ownership releases the lock when the
process exits or is killed. Test two processes with different data directories,
contention and release on abnormal exit. Do not remove/recreate the lock file on
release. No public bypass flag in v1. Ordinary Cargo commands, unrelated programs
and other user accounts are outside this coordination guarantee.

## 3. Separately named confirmation cases

Keep `full`/`smoke` as the only measurement profiles. Add `confirm-*` case IDs to
the existing three suites; use the existing repeatable `-c/--case` to select them.
A run without `-c` checks/runs every declared case, including confirmation cases.
Document explicit primary-case selection for tuning and separate full-profile
confirmation after choosing the final candidate. Smoke never confirms a gain.

- Biggie: seeded text with seed 43, 200,000 lines, 7 words of 3 ASCII characters
  (5,600,000 bytes); patterned bytes of 8 MiB + 1 with pattern `0d0a00ff`.
- tailr: seeded text with seed 43, 500,003 lines, 3 words of 17 ASCII characters
  (27,000,162 bytes), checking last lines from file and pipe; boundary inputs of
  4,095, 4,096 and 4,097 bytes generated by Biggie bytes pattern `61620a`, checking
  last lines against GNU/the independent slice oracle. The latter sizes include
  both terminated and unterminated final records.
- mkdirr: eight Biggie-generated records `path01/a/b/c` through `path08/a/b/c`,
  with absent and already-existing state checked separately; verify every parent
  directory and permission behavior.

All inputs remain reproducible Biggie CLI output with identities/hashes. Smoke
uses 1,000 lines for the confirmation text recipes and 64 KiB for the confirmation
Biggie byte recipe, retaining their seed/pattern and word shapes; the boundary and
mkdir cases remain unchanged. Confirmatory results are observations on these cases, not proof of
speed on every possible input.

The tail input sizes were reduced on 2026-10-07 to fit the initial 32 MiB per-file
budget requested by the maintainer. Seeds, word shapes, file/pipe boundaries and
small boundary cases remain the declared contracts above. These workloads do not
claim to characterize larger-file scaling.
