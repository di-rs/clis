# Reproducible CLI benchmarking research

Date: 2026-10-06. Intended audience: clis maintainers and contributors reviewing
performance changes. This is an engineering research report and design input;
the proposed harness has not been implemented or benchmarked.

## Abstract

A useful benchmark compares equivalent work, identifies the programs and inputs,
and preserves enough evidence to repeat both the procedure and its analysis.
Ten prominent Rust CLI repositories demonstrate good individual practices, but
the inspected implementations do not collectively provide a ready-made solution
for this workspace's correctness, provenance, two-baseline, and publication
requirements. The recommended approach is an original Rust CLI and library at
`tools/cli-bench`, using an identified Hyperfine version for elapsed measurements,
Biggie for all generated benchmark data, and platform-specific resource adapters.
GitHub Actions is viable for advisory comparisons and evidence publication.

Reproducibility means replaying the identified workload and measurement procedure.
It does not promise identical elapsed times, identical RSS samples, or identical
compiler output across platforms. Archived samples must support deterministic,
offline report regeneration.

## Existing workspace evidence

Issue 9 already specifies typed operations for validation, execution, measurement,
comparison and reporting. It requires exact status/stream/effect checks, immutable
binary identities, raw samples, reversed-order confirmation, explicit uncertainty,
and separate time/size/memory measurements. Its historical Biggie results remain
useful provenance, not measurements of a future harness or current candidate.
The [archived raw record](https://github.com/di-rs/clis/blob/8278432f87a7539f75c7fe6af7afb87ff198baa1/biggie/benches/results/2026-10-06/measurements.json)
and [correctness checker](https://github.com/di-rs/clis/blob/8278432f87a7539f75c7fe6af7afb87ff198baa1/biggie/benches/results/2026-10-06/check-inputs.py)
are the preserved evidence. Local paths named in that history are not shareable
artifacts.

PR 7's [tail benchmark runner](https://github.com/di-rs/clis/blob/b1b66bfde8dae1a627187644765db368a3437057/scripts/benchmark_tail.py)
generates one Biggie dataset, hashes executables and inputs, validates both Rust
versions against GNU tail before starting Hyperfine, and retains JSON samples and
candidate/baseline mean ratios. Its
[reference checker](https://github.com/di-rs/clis/blob/b1b66bfde8dae1a627187644765db368a3437057/scripts/reference_check.py)
checks GNU identity, exact stdout/stderr/status and correctness-pass timeouts.
Its [tests](https://github.com/di-rs/clis/blob/b1b66bfde8dae1a627187644765db368a3437057/scripts/tests/test_benchmark_tail.py)
exercise wrong output, unexpected status, missing reference, and identity/raw
sample retention.

The earlier prototype illustrates these requirements for an independent solution:

| Area | Observed prototype behavior | Required change |
| --- | --- | --- |
| Scenario model | Unversioned tail-only cases; success status hardcoded to zero | Versioned utility-independent cases with explicit oracles, status, environment and I/O modes. |
| Comparators | GNU tail, previous tailr and candidate tailr required together | Independent reference and revision modes; optional three-way comparison and role-specific argv. |
| Identity | Initial executable hash plus caller-supplied revision strings | Preserved executable copies, build records and hashes checked again before accepting evidence. |
| Ordering | Reference, previous, candidate, each as a complete batch | Confirmation batch in reverse order, retaining batch identity and raw order. |
| Metrics | Time and fingerprint byte size; memory explicitly unmeasured | Deliberate size comparison and separate repeated RSS sampling with native units. |
| Resources | Correctness runner kills its process group; timer uses subprocess timeout | Defined process-tree cleanup for timeout, cancellation and timer failure. |
| Reporting | Tail-specific JSON; inherited environment; no generated PR table | Versioned report, relevant environment allowlist, readable Markdown and replay command. |
| Mutation | Three read-only file/pipe cases | Reset and validate equivalent initial state before every warmup and sample. |

Its [workflow](https://github.com/di-rs/clis/blob/b1b66bfde8dae1a627187644765db368a3437057/.github/workflows/benchmarks.yml)
already separates candidate/baseline build directories, selects one compiler,
pins Hyperfine 1.20.0, defines Linux/macOS runners, and uploads artifacts for 30 days.
It is weekly/manual, not a PR-comment workflow. The inspected
[status document](https://github.com/di-rs/clis/blob/b1b66bfde8dae1a627187644765db368a3437057/docs/ci-guardrails-status.md)
labels full timing and remote benchmark evidence pending. Configured jobs alone
do not establish successful benchmark execution.

The local [tail Nushell runner](../../coreutils/tailr/benches/tail.bench.nu) still
has the documented stale input path and blanket ignored failures. PR 7 repairs
that entry point. Neither its code nor its workflow shape constrains the new
implementation. As of planning, PR 7 has advanced to `de152a92a9ca399fd256cd0bf9b7667f4e106230`;
its updated runner uses process-group timeout cleanup and explicit Biggie `text`
syntax. The preceding findings remain an audit of the earlier pinned revision.

### Source observations and lessons

**ripgrep.** The [Python benchsuite](https://github.com/BurntSushi/ripgrep/blob/3fce3b5bb0236da2df6d99672afb8a719642eca7/benchsuite/benchsuite)
uses one warmup and three measured runs by default, calculates timing statistics,
and records commands, environment, duration and result-line counts. It compares
GNU grep, git grep and other search tools. Its Linux-tree/subtitle corpora are
not fully checksum-pinned by the downloader. The runner captures stdout for
counting, discards stderr and does not enforce return codes or equal results.
[Historical runs](https://github.com/BurntSushi/ripgrep/tree/3fce3b5bb0236da2df6d99672afb8a719642eca7/benchsuite/runs)
preserve useful raw data and host descriptions. Borrow workload organization and
evidence retention; make correctness a prerequisite in our runner.

**fd.** The separate [fd-benchmarks regression runner](https://github.com/sharkdp/fd-benchmarks/blob/57389548465bbc580fbc5322690b1e5d81462ac4/regression.sh)
compares supplied `fd-master` and `fd-feature` executables and produces JSON and
Markdown. Its [configuration](https://github.com/sharkdp/fd-benchmarks/blob/57389548465bbc580fbc5322690b1e5d81462ac4/config.sh)
defaults to the author's home directory and includes privileged Linux cache
clearing. An optional [comparison helper](https://github.com/sharkdp/fd-benchmarks/blob/57389548465bbc580fbc5322690b1e5d81462ac4/prelude.sh)
sorts/diffs output after timing and warns rather than rejects. Use the executable
role model, but replace the corpus and validation procedure. The inspected
benchmark repo has no license file; its scripts must not be copied under the
main fd repository's assumed license.

**bat.** Its [runner](https://github.com/sharkdp/bat/blob/4608fc959aa8abf80d32198836511a570b7ae9ea/tests/benchmarks/run-benchmarks.sh)
clears configuration/pager/theme environment and uses `--no-config`. It separates
startup, syntax detection, highlighting, wrapping and many-small-file work, with
three warmups and ten measurements by default. Each invocation selects one binary.
The wrapping variants share export filenames because the wrap parameter is omitted
from the path. Our scenario/artifact identity must include every varied factor.

**eza.** The inspected [Criterion benchmark](https://github.com/eza-community/eza/blob/471bfbc7b03cbac8c738e8d9050edb06ee79132a/benches/my_benchmark.rs)
measures logger configuration. Criterion configuration in a manifest is not proof
of an external `ls` comparison. No benchmark invocation was found in the inspected
unit-test workflow or justfile. Keep component and CLI results distinct. Current
package licensing is EUPL-1.2 with historical MIT notices in some files; implement
our own design rather than assuming current files are importable as MIT.

**uutils.** Its [performance guide](https://github.com/uutils/coreutils/blob/d027897a2cc3d220d92930e3a81f7025e020e4c0/docs/src/performance.md)
explicitly describes GNU, old and new implementations. The
[rm runner](https://github.com/uutils/coreutils/blob/d027897a2cc3d220d92930e3a81f7025e020e4c0/src/uu/rm/benchmark.sh)
uses Hyperfine preparation to recreate mutation inputs. Separately,
[benchmark CI](https://github.com/uutils/coreutils/blob/d027897a2cc3d220d92930e3a81f7025e020e4c0/.github/workflows/benchmarks.yml)
selects changed packages and runs CodSpeed simulation/memory with Divan-compatible
benches. Those benches call utility entry functions in-process; they omit ordinary
process launch. Hosted service policy was not audited. Borrow the three-role
comparison and package selection, while keeping measurement types separate.

**Hyperfine.** Version 1.20.0 exports
[raw times and exit codes](https://github.com/sharkdp/hyperfine/blob/975fe108c4ee7bd2600d10758207b44ca3dae738/src/benchmark/benchmark_result.rs),
with statistics and resource fields. The scheduler completes each command's batch
before the next. Current default-branch code is 2.0.0-alpha.1 and changes JSON
structure and shell defaults; do not develop against moving master documentation
while invoking 1.20.0. The detailed integration limits below are based on the
1.20.0 tag and the locally installed 1.20.0 help.

**uv.** The [external wrapper](https://github.com/astral-sh/uv/blob/151e0156b5f4f2a27fb7dbd820fc130d4dab037a/scripts/benchmark/src/benchmark/__init__.py)
and [resolver scenarios](https://github.com/astral-sh/uv/blob/151e0156b5f4f2a27fb7dbd820fc130d4dab037a/scripts/benchmark/src/benchmark/resolver.py)
support named binary paths, per-tool arguments, temporary work directories, and
cold/warm/incremental workloads. Setup checks and command success do not establish
cross-tool output equivalence. Its separate [CI](https://github.com/astral-sh/uv/blob/151e0156b5f4f2a27fb7dbd820fc130d4dab037a/.github/workflows/bench.yml)
runs internal CodSpeed benchmarks and retains profile metadata. Adopt explicit
cache states and identities; do not equate these internal measurements with CLI
comparisons.

**mise.** [tak configuration](https://github.com/jdx/mise/blob/d2b4b659e9336d187f428245af83e9f4ec942c79/tak.toml)
defines argv and offline workloads. Its [PR workflow](https://github.com/jdx/mise/blob/d2b4b659e9336d187f428245af83e9f4ec942c79/.github/workflows/perf-pr.yml)
compares head and merge base, produces Markdown, and separates measurement from
comment publishing. It restricts who can run measured PR code and enforces an
instruction-count gate. The older [walltime script](https://github.com/jdx/mise/blob/d2b4b659e9336d187f428245af83e9f4ec942c79/xtasks/test/perf)
interleaves binaries but defaults to one measured run and masks failure with
`|| true`. Adopt the publication boundary, not those failure or enforcement rules.

**Nushell.** [Tango benchmarks](https://github.com/nushell/nushell/blob/3b08da67d19de7982a6612bca1eea4009fee2f9b/benches/benchmarks.rs)
cover parsing, evaluation and other library operations. The
[comparison script](https://github.com/nushell/nushell/blob/3b08da67d19de7982a6612bca1eea4009fee2f9b/toolkit/benchmark.nu)
builds both revisions and retains 50-sample paired comparisons, but changes the live
checkout. Our build orchestration should use isolated source/build directories and
leave the contributor's active checkout intact.

**Starship.** [Module timing](https://github.com/starship/starship/blob/d4d0459c5c24ba8f64663af8714f7858d7fb357b/src/modules/mod.rs)
and the [timings command](https://github.com/starship/starship/blob/d4d0459c5c24ba8f64663af8714f7858d7fb357b/src/print.rs)
expose current-environment latency. No dedicated benchmark suite was found in the
inspected tree, Cargo manifest and main workflow. A bench profile or diagnostic
timer alone is insufficient evidence for comparative performance claims.

## Measurement controls required in our solution

### Biggie owns generated benchmark content

Use Biggie `text`, `records`, `fields`, `bytes` and `pair` as appropriate. Every
scenario records an explicit seed or literal pattern/schedule. Generate once in
untimed preparation and make every comparator consume the same bytes. A saved
dataset recipe must include the generator source/build/binary identity and the
resulting file size and SHA-256. Checksums detect a changed dataset; they do not
prove it has the intended record count, encoding or shape.

[Biggie's contract](../../biggie/README.md#cargo-features-and-rust-api) limits seeded
reproducibility to the same options, build and platform. Keep exact input bytes
when exact future replay matters. Preserve the recipe even when distributing the
data would be too large. The harness may create/reset directories and validate
paths; it must not introduce a competing synthetic payload generator. For mkdirr,
Biggie records can supply a deterministic path list while the harness owns the
disposable filesystem structure. Ordinary harness test fixtures are distinct
from measured benchmark datasets.

When benchmarking Biggie itself, baseline equality can preserve a shared bug.
Independently validate byte budgets, literal record schedules, line/field counts,
or pair ordering/overlap. Freeze the fixture-generator identity independently of
the Biggie binaries under comparison. Role-specific argv accommodate the older
root syntax and newer explicit subcommands without claiming unequal work matches.

### Equivalent work precedes timing

Validate stdout bytes, exact status, expected stderr and relevant filesystem
effects in disposable sandboxes. Compare equivalent supported options, not
unsupported flags that return quickly. Narrow, explicit diagnostic normalization
may remove a program name or sandbox prefix; blanket trimming/sorting can hide
real differences. Failure blocks that case's performance evidence. Do not silently
drop the failed case from the summary.

Declare file operands, regular-file stdin and pipe stdin separately. Also declare
stdout sink: null, drained pipe or regular file. Some tools recognize `/dev/null`
and avoid work; equal sinks alone do not establish the intended user workload.
Throughput uses a declared, meaningful amount of work. Dividing the whole input
file size by the time for seek-based `tail -c 10` would falsely imply that all bytes
were processed.

Mutation cases require the same initial filesystem state before every correctness
pass, warmup, timing sample and memory sample. Reset happens outside timing unless
the scenario explicitly measures reset too. Fresh directories, existing directories,
permission errors and durable storage are different cases. Cached writes are not
durable writes. No privileged machine-wide cache clearing is proposed.

### Hyperfine is an adapter boundary

Pin/support identified engine versions and retain native JSON and diagnostics.
The 1.20.0 [executor](https://github.com/sharkdp/hyperfine/blob/975fe108c4ee7bd2600d10758207b44ca3dae738/src/benchmark/executor.rs),
[I/O policies](https://github.com/sharkdp/hyperfine/blob/975fe108c4ee7bd2600d10758207b44ca3dae738/src/options.rs),
and [benchmark loop](https://github.com/sharkdp/hyperfine/blob/975fe108c4ee7bd2600d10758207b44ca3dae738/src/benchmark/mod.rs)
establish these implementation constraints:

- Select shell mode explicitly. Direct mode still receives a parsed command
  string, so an argv-to-string adapter needs round-trip tests for spaces, quotes,
  empty arguments and metacharacters. No free-form shell interpolation by default.
- `--input FILE` supplies a regular file descriptor, not a pipe. Pipe scenarios
  require an explicit, documented producer and measurement boundary.
- `--ignore-failure=1` allows zero as well as one. Measured exit codes can be
  checked afterward; discarded warmup statuses cannot. Exact expected nonzero
  behavior needs explicitly checked warmups and per-sample validation or a
  checked adapter with its overhead declared. Blanket ignored failures are invalid.
- Setup/prepare/conclude/cleanup hooks have different timing boundaries. Hook
  failure can interrupt cleanup; the harness still owns final resource cleanup.
- Commands run in sequential batches. Use a separately recorded reversed-order
  confirmation batch, or a future explicitly implemented scheduling policy.

These are adapter acceptance requirements, not permission to replace the whole
timing engine with an unvalidated custom stopwatch.

### Report time, size and memory separately

Follow issue 9's starting policy: three warmups and at least 20 measured runs per
batch, followed by reversed-order confirmation. Allow recorded exceptions for
expensive workloads. Report mean, median, sample standard deviation, sample count,
absolute change and candidate/baseline ratio. Name the statistic used for a claim;
standard deviation is not a confidence interval. Preserve outliers, batch identity,
tool warnings and raw samples. Conflicting batch direction or material uncontrolled
noise is inconclusive. Do not infer equivalence merely from failure to detect a
difference or introduce an arbitrary percentage merge threshold.

Record executable logical byte size and SHA-256 once per retained binary. Record
target, compiler, profile, features, optimization/linker flags, PGO and stripping
policy. Old/new source comparisons should use the same selected toolchain and
build policy. An external GNU binary may have different build provenance: disclose
that as a product comparison rather than pretending build settings match.

For RSS, collect at least five fresh process samples separately from elapsed
measurements. Keep platform-native output/units and normalized bytes, with median
and range. Use identified Linux/macOS adapters, document whether descendants are
included, and never translate missing metrics to zero. One input size does not
prove bounded memory. Keep instrumented measurements separate from ordinary runs.

## Implementation options

| Approach | Strengths | Costs and limitations | Assessment |
| --- | --- | --- | --- |
| Rust CLI/library with Hyperfine adapter | Fits workspace library/API/testing policy; typed scenarios and errors; one installed executable; reusable report/validation operations | More implementation effort for process lifecycle, schema and OS adapters; Hyperfine remains an external dependency | Recommended for the durable subsystem. |
| Python package with Hyperfine adapter | Extends PR 7 naturally; strong standard-library subprocess, JSON, TOML and platform support | Python runtime/version becomes another requirement; reusable API is Python rather than the workspace's Rust operation model | Credible smaller orchestrator if implementation speed becomes the priority. |
| Hosted benchmarking product plus thin local runner | Existing dashboards, PR integrations and controlled execution options | Service integration and policy ownership; still needs Biggie generation and CLI equivalence checks | Optional future exporter, not the initial execution dependency. |

Reuse Clap and existing diagnostics conventions at the CLI boundary; use typed
serialization, hashing, temporary resources and small OS adapters in the library.
Candidate Rust dependencies include Serde, TOML, SHA-256 and tempfile libraries,
subject to the repository's dependency review. Exact versions and feature sets
belong in the implementation plan and lockfile. Do not add a TUI framework now.

Criterion, Divan and Tango remain useful for later Rust operation microbenchmarks.
They do not automatically validate external commands or include process startup.
Criterion's [CI guidance](https://bheisler.github.io/criterion.rs/book/faq.html#how-should-i-run-criterionrs-benchmarks-in-a-ci-pipeline)
warns about virtualized-host noise and false detections. Instruction simulation is
another metric, not elapsed I/O time. [CodSpeed](https://codspeed.io/docs/instruments)
distinguishes simulation, walltime and memory, and recommends walltime for I/O-heavy
work. [Bencher](https://bencher.dev/docs/explanation/adapters/)
accepts Hyperfine JSON and custom metrics; that makes future integration possible
without surrendering the local scenario/evidence format.

## Recommended subsystem boundaries

This is a proposal for design review, not an approved implementation specification.

| Operation | Responsibility |
| --- | --- |
| Prepare/build | Resolve Git refs to SHAs; build selected packages under one toolchain/policy in isolated source and target directories; preserve binaries and build records. Accept prebuilt paths with declared provenance completeness. |
| Check | Parse/version-check a suite, resolve executable roles, generate or verify Biggie data, validate byte/status/effect assertions and resource bounds. |
| Run | Execute checked cases with declared input/output modes, resets, timeouts, confirmation ordering, timing and separate resource sampling. |
| Compare | Analyze compatible saved evidence deterministically; reject mismatched scenarios/data/measurement modes and distinguish unavailable, invalid and inconclusive results. |
| Report | Produce terminal, JSON and Markdown output from the same result model, with exact identities, raw-evidence links and a portable replay recipe. |

Use named executable roles (`reference`, `previous`, `candidate`, `generator`)
instead of assuming all utilities share argv or have a GNU original. Biggie needs
only revision comparison; tailr/mkdirr can use both modes. Reject nonexistent refs,
overwritten artifacts, incompatible builds and stale input hashes. Do not replace
a missing requested reference with whatever binary happens to be on PATH.

Library operations accept typed options and explicit paths, executables and output
writers. They return structured outcomes/errors without parsing argv, installing
logging, changing global cwd/environment or exiting the process. Adding the Rust
package at the requested location requires an explicit workspace-member update;
the current member globs do not include `tools/`.

Version the human-edited suite, resolved run manifest and result schema. Separate
portable role/path bindings from the exact resolved paths recorded for an executed
run. Store all raw data, tool/version identity, dataset hashes, run order and
failure outcomes. Report generation must work offline without rerunning commands
or consulting an LLM. Cross-machine historical results may be displayed alongside
each other but cannot establish an implementation speedup.

The proposed initial workloads are:

| Utility | Workload | Main correctness checks |
| --- | --- | --- |
| Biggie | Literal records, patterned bytes and seeded text; previous versus candidate | Exact literals/byte budgets, independent structure checks, output comparison for compatible seeded builds. |
| tailr | Last lines and bytes from files; last lines from a real pipe; tiny and larger inputs | Exact GNU comparison of stdout/status/stderr, Biggie dataset hashes, preserved access/sink policy. |
| mkdirr | GNU `mkdir -p` versus mkdirr on absent nested paths, with per-run reset | Expected path/type set, relevant mode behavior, no unexpected effects, exact status/stderr. |

`mkdirr` defaults to parent creation whereas GNU requires `-p`; the explicit
reference argv preserves equivalent semantics. Its current unsupported permission
options are not benchmark scenarios. These cases prove reuse without claiming
coverage of every utility or implementing unrelated compatibility fixes.

## GitHub Actions feasibility

Implement measurement as a CLI used by a reusable workflow. A composite action can
later package installation and invocation; the reusable workflow better expresses
the initial Linux/macOS jobs and separate publisher. GitHub documents that
[reusable workflows own jobs whereas composite actions own steps](https://docs.github.com/en/actions/concepts/workflows-and-actions/reusing-workflow-configurations).

Build both Rust revisions before measurement and benchmark them on the same job's
machine, with no concurrent build/test workload. Resolve exact PR head and baseline
SHAs; do not accidentally label GitHub's synthetic merge checkout as the candidate
head. The baseline policy should be visible: merge-base for attribution of a PR's
changes, with explicit refs supported for other comparisons. Do not use a timing
from yesterday's different runner as today's denominator.

The measurement workflow runs untrusted PR code with read-only permissions and
without secrets. It uploads a versioned JSON evidence bundle and writes a
[Markdown job summary](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/workflow-commands-for-github-actions#adding-a-job-summary).
Advisory comparisons can run on GitHub-hosted machines, with shared-host limitations
prominent. Correctness/schema/process errors fail the job; timing increases do not.
Native Linux/macOS outcomes remain separate.

A trusted publishing workflow updates one marked comment per PR. It must not
execute scripts, binaries, or shell commands from the PR or its artifacts. Validate
artifact schema/size, source workflow/repository/run identity, PR association and
head SHA; construct Markdown from bounded data; escape untrusted strings; link
the actual run and artifacts. Avoid stale runs overwriting a newer report. Keep
the token's comment-writing permission out of benchmark execution. GitHub's
[security guidance](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)
explicitly covers privileged PR execution and untrusted `workflow_run` artifacts.

PR comments should contain per-scenario results for both comparator relationships,
correctness outcome, sample counts, uncertainty/warnings, metrics with units, a
copyable replay command and evidence links. The full archive contains the resolved
suite, identities, raw results and preparation/validation records. Do not upload
an unrestricted environment dump or pretend local `/tmp` paths are downloadable.

Artifact retention is a real reproducibility constraint: GitHub supports
[configurable retention](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#configuring-the-retention-period-for-checks-workflow-runs-commit-statuses-artifacts-and-logs-in-your-repository),
subject to repository/organization limits. Proposed default: 90 days for PR evidence,
with expiry visible in reports and an exportable bundle for longer preservation.
Retain versioned scenarios in Git; accepted long-term performance claims should
also preserve compact raw records in Git or durable storage. Rebuilding from a
recipe after an artifact expires is a new measurement, not recovery of old samples.

## Implementation acceptance and accepted design

Before product code, review the written design and implementation plan. The
acceptance matrix should include malformed/unknown schemas, failed correctness
gates, unavailable references, valid nonzero statuses, changed hashes, incompatible
reports, quoted/empty/non-UTF-8 arguments where supported, real-pipe semantics,
mutation resets, timeout/cancellation descendants, partial evidence, report escaping
and stale PR updates. No ordinary test should depend on machine speed or network.

Prove both comparison modes on the initial three utilities with Biggie-generated
inputs. An identical-binary comparison can validate plumbing but is not an
optimization result. Record actual tool/platform outcomes; do not claim Linux
verification from macOS execution or CI configuration. Follow package and workspace
checks in CONTRIBUTING for the eventual Rust implementation.

The maintainer accepted Rust/Hyperfine, warm-cache first scope, PR merge-base policy
and the evidence-retention approach. The linked design and implementation plan
specify exact nonzero warmup handling, pipe measurement boundaries, resource adapter
semantics and timeout cleanup; implementation must verify those contracts before
describing the capabilities as working. TUI, instruction and allocation
profiling, cold-cache automation, hosted dashboards, and migration of every utility
remain outside the agreed initial scenario set.

## Additional review: agentic optimization

Reviewed on 2026-10-06: Max Woolf's
[agentic iteration article](https://minimaxir.com/2026/09/agentic-iteration/), its
[optimization prompt](https://gist.github.com/minimaxir/933cd6354d96e1fbb45bea13e0940952)
and [Rust agent guidance](https://gist.github.com/minimaxir/86de3cc8f628079d8337e70924b3411d).
These are research inputs, not instructions governing this repository.

The article describes repeated optimization against a starting baseline, diverse
workloads and reference-output checks. It also reports apparent gains obtained by
removing required work. Its examples primarily concern libraries and algorithms;
several showcased implementations were still awaiting release when published.
We have not independently reproduced their speedups. This supports improving
measurement controls, not assuming similar gains for these CLIs.

The maintainer accepted these four adaptations on 2026-10-06 and authorized
continued implementation. They are incorporated into the design and task checks;
concrete interface choices are resolved before their respective implementation.

| Proposed adaptation | Current coverage and concrete addition |
| --- | --- |
| Freeze the measurement contract during an optimization experiment | Existing records retain suites, inputs and build identity. Also record the harness executable identity and validator/analysis policy, and explicitly show changes to scenarios, correctness rules or measured work. An altered workload starts a distinct experiment; rerun all selected binaries under that same contract. Hashes expose changes but do not prove that an oracle is correct. |
| Use separate confirmation workloads | Existing full/smoke profiles measure different sizes, but smoke is a wiring check. Define additional Biggie-generated confirmation cases with different seeds, sizes and boundary shapes, and validate the final candidate on them after tuning. Preserve exact recipes/hashes; do not use smoke results as performance confirmation. |
| Enforce one measurement session per host | The current scheduler is sequential and CI separates build/test from timing. Add a cross-process lock shared by cooperating harness invocations, including different data directories, with a contention regression. Document that it cannot exclude unrelated workloads or guarantee an idle host. |
| Make optimization attempts traceable | Retain a fixed starting SHA, hypothesis/change summary and links to every attempted run, including rejected/no-improvement attempts. Existing explicit revision selection can rerun the fixed baseline and candidate together; no historical timing becomes a new speedup denominator. A small experiment record is sufficient; autonomous code editing is separate scope. |

Keep whole-command measurements in Hyperfine. Criterion's
[function-comparison interface](https://bheisler.github.io/criterion.rs/book/user_guide/comparing_functions.html)
would be useful later for an identified library hotspot, with distinct measurement
scope. Its [FAQ](https://bheisler.github.io/criterion.rs/book/faq.html) also documents
CI noise and false detections; a statistical result does not eliminate the need for
a fresh final confirmation run.

Do not import the external prompts wholesale. Our exact CLI correctness gate,
stored raw evidence, explicit warm-cache workloads and advisory reporting remain
binding. Fixed speedup quotas, unconditional cache disabling and blanket compiler-
flag bans would conflict with those choices. Build differences must remain explicit
and appropriately labelled; implementation changes still require measured evidence.
